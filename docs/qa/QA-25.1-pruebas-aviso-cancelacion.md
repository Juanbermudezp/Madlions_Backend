Mientras el endpoint de cancelación (BE-7.1) no esté en develop, la prueba e2e hace lo mismo que hará ese endpoint: en una transacción pasa la clase y sus reservas "Confirmada" a CANCELADA_GIMNASIO y, después de confirmarla, llama a `AvisosClaseService.avisarCancelacion()`. Datos: una clase con 2 reservas confirmadas (una con Set de clases), 1 reserva cancelada por el miembro y un miembro sin reserva. Todo lo que crea se borra al terminar (usuarios `qa25-`, tipo de clase y planes `[QA-25.1]`).

## Integración con BE-7.1 (para David)

1. En `ClasesModule` (o el módulo donde viva la cancelación): `imports: [AvisosModule]`. AvisosModule ya no importa otros módulos, así que no hay dependencia circular.
2. Inyectar `AvisosClaseService` (de `@Avisos/services`).
3. Dentro de la transacción, antes de cancelar las reservas, leer las CONFIRMADA de la clase con el `tipoPlan` de su membresía y armar los afectados:

   ```ts
   const afectados = confirmadas.map((r) => ({
     miembroId: r.miembroId,
     devolvioCredito: r.membresia.tipoPlan === TipoPlan.SET_CLASES,
   }));
   ```

4. Después de confirmar la transacción:

   ```ts
   await this.avisosClase.avisarCancelacion(clase.id, afectados, motivo);
   ```

   El método nunca lanza: si el envío falla, la cancelación no se revierte y el error queda en el log. Repetir la llamada no duplica avisos (referencia `clase-{id}-cancelada`).
